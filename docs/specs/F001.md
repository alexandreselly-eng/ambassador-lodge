# F001 — Sas de validation avant toute écriture en base

> `tests` et `commande_test` sont volontairement vides : la doctrine v1.2 interdit à
> `workflow-status` de les écrire. Ils seront proposés par le pilote et validés à la main.
> Candidats identifiés : `tests/garde-fou.test.ts`, `tests/ecritures.test.ts`.

## Ce que la fonctionnalité fait

Rien n'entre dans `data_snapshots` sans passer par `AL_VALID.openGate()`. La synchro API remplit
`sh_pending`, un sas, et ne décide pas. La modale présente le différentiel, l'utilisateur tranche.

## Pourquoi deux garde-fous à seuils différents

`SUPPRESSION_MASSIVE()` côté application arrête **l'accident**, avec une confirmation possible à
l'écran. Le déclencheur `garde_fou_effacement` en base arrête la **catastrophe**, quel que soit
le client. Aligner les deux seuils ferait échouer toute suppression légitime confirmée à l'écran
sur une erreur SQL incompréhensible.

## Le piège que cette fonctionnalité protège

`commit()` fait `upsert({ rows: sub })` : il **ne fusionne pas**. Tout appelant qui transmet un
jeu partiel efface le reste. Les deux garde-fous et l'archivage préalable existent pour ça.
